# [SPEC] Book as guest, pay by card / Apple Pay / Google Pay

## Meta
- **Status:** Validated
- **Classification:** 2. Project Primitive
- **Target:** zedslot V0
- **Story:** `docs/stories/book-as-guest-card.md`
- **Author:** Agent (Spec)
- **Date:** 2026-05-03

## Problem

Little Biceps visitors currently go through Shopify cart → checkout → BookThatApp, leaking conversions at every step. The guest booking flow must let a first-time visitor pick a service, practitioner, slot, and pay by card — all on one mobile-first screen — without account creation, cart, or page navigation.

## Solution

A hosted booking page at `book.<merchant>.com` that renders a linear service → practitioner → slot → pay flow as a single scrollable screen. Payment is via Stripe Payment Element (card + Apple Pay + Google Pay). No auth required. Booking is confirmed on payment success; 15-min pending hold on slot selection.

## Scope

### In Scope
- Service picker (list from active services for tenant)
- Practitioner picker (filtered by service eligibility; auto-select if single)
- Room auto-assignment (first available eligible room — transparent to customer)
- Slot picker (next 14 days, generated by `booking-engine.listAvailableSlots`)
- Customer info form (name, email, phone — minimal, no account)
- Stripe Payment Element integration (card, Apple Pay, Google Pay)
- PaymentIntent creation with idempotency key = `booking.id`
- Booking creation (`pending` → `confirmed` on payment success)
- Confirmation screen with "add to calendar" links
- PostHog funnel events: `slot_viewed`, `slot_selected`, `checkout_loaded`, `payment_submitted`, `payment_succeeded`, `payment_failed`
- 15-min slot hold (pending booking)

### Out of Scope
- Pack/gift-card credit redemption (see `specs/redeem-pack-credit.md`)
- Email notifications (see `specs/confirmation-and-reminder-emails.md`)
- Cancel/reschedule (see `specs/customer-cancel-or-reschedule.md`)
- Admin configuration (separate specs)
- A/B testing harness
- Shopify order writeback (P1)

### API / Interfaces

#### `GET /api/services?tenantId={id}`
Returns active services for a tenant.
```ts
Response: { services: Array<{ id, name, durationMinutes, priceCents, requiresResource, requiresRoom }> }
```

#### `GET /api/slots?serviceId={id}&resourceId={id?}&from={iso}&to={iso}`
Returns available slots for the next 14 days.
```ts
Response: { slots: Array<{ startsAt: string, endsAt: string, resourceId: string | null, roomId: string }> }
```
Performance budget: p95 < 400ms. Tenant resolved from hostname.

#### `POST /api/bookings`
Creates a pending booking + payment intent.
```ts
Request: {
  serviceId: string;
  resourceId?: string;
  roomId: string;
  startsAt: string; // ISO 8601
  customer: { name: string; email: string; phone?: string };
}
Response: {
  bookingId: string;
  paymentIntentClientSecret: string;
  expiresAt: string; // 15 min from now
}
```
Idempotency: If called with the same `(tenantId, serviceId, resourceId, roomId, startsAt, customerEmail)` within 15 min and a pending booking exists, return the existing booking.

#### `POST /api/bookings/{id}/confirm`
Called by Stripe webhook (`payment_intent.succeeded`). Transitions booking `pending` → `confirmed`.
```ts
Idempotency: Replaying the same webhook never confirms twice (checked by payment status).
```

#### `POST /api/bookings/{id}/fail`
Called by Stripe webhook (`payment_intent.payment_failed`). Transitions booking `pending` → `cancelled`, releases slot.

### Booking Flow State Machine

```
[idle] → select_service → select_practitioner → select_slot →
  → POST /api/bookings (creates pending booking + PI)
  → [slot_held] → Stripe Payment Element confirm
    → payment_intent.succeeded webhook → confirmed ✓
    → payment_intent.payment_failed webhook → cancelled, offer retry
    → 15min timeout → expired, slot released
```

### Idempotency

| Operation | Key | Behavior |
|-----------|-----|----------|
| Create booking | `(tenantId, serviceId, resourceId, roomId, startsAt, email)` | Return existing pending booking if within 15min hold |
| Create PaymentIntent | `booking.id` | Stripe deduplicates via `idempotency_key` |
| Confirm booking | `payment.stripePaymentIntentId` | Skip if already `confirmed` |
| Fail booking | `payment.stripePaymentIntentId` | Skip if already `cancelled` or `confirmed` |

## Edge Cases

| Scenario | Expected Behavior |
|----------|------------------|
| Slot taken between pick and payment | `canBook` pre-check returns conflict → 409 with next-available suggestion |
| Two customers race for same slot | DB EXCLUDE constraint → one wins, other gets 409 |
| Payment fails (card declined) | Booking stays `pending`; user retries on same hold. After 15min → auto-cancelled |
| Payment requires 3DS | Stripe handles 3DS flow; booking stays `pending` until webhook confirms |
| Network error during payment confirm | Client retries; idempotency key prevents double-charge |
| Webhook arrives before client redirect | Booking confirmed via webhook; client polls `/api/bookings/{id}` for status |
| Webhook replayed | Idempotency check on payment status — no duplicate confirm |
| Service disabled between slot pick and payment | `canBook` checks service status; rejects with "service unavailable" |
| Browser closed during payment | Hold expires at 15min; slot released; no charge |
| Apple Pay / Google Pay not available | Payment Element falls back to card form automatically |
